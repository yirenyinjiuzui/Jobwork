# v1.1.9 测评完成回执验收

负责方：原监督任务。基线为已验收的 v1.1.8；未建新项目，未改默认 data、历史包或外部来源。

## 复现与修复

隔离复现：同一投递先收到 A-1、B-2 两个不同测评邀请，A-1 完成回执会将整个投递改为 waiting 并清空 B-2 截止。这会漏掉仍需完成的任务。

本轮使用已有 settings 表保存每条投递下按测评编号分开的待办，保留编号、截止及精度、通知时间与完成标记；无需新增表或列。台账显示“各测评状态”。还有待完成测评时，以最早已知截止作为本条投递的待办截止；全部已完成才进入等待结果。原来已有面试、Offer 或关闭状态，不因测评回执倒退。

.eml 完成回执必须身份足够明确、唯一匹配投递、对应已知测评编号，且发送时间明确并晚于该测评最后有效通知。预览本身不写入；用户明确勾选“确认仅完成测评 XXX”后才结束该测评。缺编号、泛化第三方回执、多个可能对象或时间不明确，保持人工复核，不能靠勾选通用复核清空待办。

已完成标记持久保留，重复回执不增加重复历史；旧延期和同编号后续提醒都不能自动重开。完成 A 时只核对 A 的时序，不把独立 B 的较新通知时间误当成 A 的时间。原邀请、延期、完成证据与不能应用的通知均可查看历史。中英文条件式“如果通过将邀请面试”不会变成明确面试邀请。

## 旧库兼容

旧库已有的当前测评编号、截止和通知时间，在读取时映射为一个未完成测评，读操作不写原库；首次确认相关事件后才存入明细。旧版仅保存的一个编号不能用来恢复已经丢失的多测评信息；无可靠编号的旧记录不会被自动完成。旧 application ID、全部原字段、历史与表结构保持可读，解压验收使用归档 v1.1.8 实际创建的虚构库核对。

## 一次离线验收

沿用 [核心离线流程](OFFLINE-CORE-ACCEPTANCE.md)，在同一 Fictional Core Loop 投递的两次延期之后、面试邮件之前：

1. 导入 `tests/fixtures/core-loop/07-second-test.eml`，确认建立 LOOP-TEST-2。此时 LOOP-TEST-1 与 LOOP-TEST-2 分别显示待完成。
2. 预览 `08-completed-first.eml`。不勾选完成确认时，不能清待办；勾选“确认仅完成测评 LOOP-TEST-1”后，只结束第一项。第二项仍截止 2026-11-08 12:00 香港，投递仍处于测评。
3. 导入 `09-completed-second.eml` 并单独确认，进入等待结果，测评截止清空。两项完成标记和原证据均保留。
4. 重导入 08，以及旧的 03-extension.eml，不能重开测评。然后按原流程导入 05-interview.eml，确认真实的面试邀请才能进入面试。

样例日期固定，不修改系统时间，不使用真实资料。Windows 启动演练库可在 PowerShell 运行 `.\start-windows.cmd --data data\completion-demo-01.sqlite3 --interval 0`，先确认此演练文件不存在；再次演练换新名字，保留旧库。
